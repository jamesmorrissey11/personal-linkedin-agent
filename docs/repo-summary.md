# Repo: `personal-linkedin-agent` — Structured Summary

This is a **single-stack Python project** (no frontend/backend split) with a supporting **IaC stack** for Azure provisioning.

## 1. Python Agent Stack

**Purpose:** AI-powered LinkedIn automation — decides whether to accept/ignore connection invitations and triages inbox messages by urgency, using an LLM (Azure OpenAI via Pydantic AI) driving a Playwright browser session.

### Modules / Entry Points

| File | Role |
|---|---|
| `invitations_manager.py` | Main entry point (`python invitations_manager.py --num-to-process N [--record-eval-cases] [--headless]`). Logs into LinkedIn via Playwright, scrapes invitation cards, runs a `pydantic_ai.Agent` to decide accept/ignore/undecided, executes the click, and can fall back to full-profile scraping when undecided. |
| `inbox_manager.py` | Secondary entry point (`python inbox_manager.py --num-messages N`). Scrapes recent LinkedIn conversations, ranks each by urgency (1–10) via a second `Agent`, and opens the highest-priority thread. |
| `evals.py` | Runs `pydantic_evals` regression tests against `linkedin_invitation_cases.yaml` using `CorrectDecisionEvaluator` + `IsInstance`. |

### Data Layer

No database — state is file-based:
- `playwright/.auth/state.json` — persisted browser session/cookies (created at runtime, gitignored presumably).
- `linkedin_invitation_cases.yaml` — append-only eval dataset (20 hand/agent-generated cases), doubles as both regression fixture and a live log when `--record-eval-cases` is used.
- `.env` (generated by `write_dot_env.sh/ps1` post-provision) — Azure OpenAI endpoint/deployment config.

### Templates

None (no Jinja/HTML) — prompts are inline Python f-strings/system prompts embedded directly in `invitations_manager.py` and `inbox_manager.py`.

### Scripts

None beyond the two CLIs above; no Makefile/task runner.

## 2. Infra Stack (Azure Developer CLI / Bicep)

**Purpose:** Provisions an Azure OpenAI resource (`gpt-5.5` deployment) for the agents to call.

### Modules

- `infra/main.bicep` — subscription-scoped Bicep provisioning a resource group + Cognitive Services (OpenAI) account/deployment with RBAC role assignment (`Cognitive Services OpenAI User`).
- `infra/main.parameters.json` — azd parameter bindings.
- `infra/write_dot_env.sh` / `.ps1` — postprovision hooks writing `.env` from Bicep outputs.
- `azure.yaml` — azd project manifest wiring the hooks.
- `.github/workflows/azure-dev.yaml` — CI provisioning via `azd provision` on push to main (federated OIDC creds).
- `.github/workflows/template-validation.yaml` — internal Microsoft sample-template best-practices check (explicitly marked deletable in forks).

## Tech-Debt Areas

- **Two inconsistent Azure OpenAI client setups**: `invitations_manager.py` uses `azure.identity.aio.AzureDeveloperCliCredential` + `openai/v1` base URL + `OpenAIChatModel`; `inbox_manager.py` uses sync `azure.identity.DefaultAzureCredential` + different base URL + deprecated `OpenAIModel`. Divergent auth/model classes = duplicated, drifting logic.
- **Heavy DOM-scraping via brittle CSS selectors/aria-labels** (LinkedIn markup can change silently) — no abstraction layer or selector versioning; multiple selector fallback chains hard-coded inline.
- **No automated tests** beyond `evals.py` (LLM-output evals, not unit tests) — no pytest suite for scraping logic, YAML parsing, or CLI argument handling.
- **Broad `except Exception`** swallowing in `inbox_manager.py` (e.g., `get_logged_in_user_name`, message extraction) — silently degrades to "Unknown" without surfacing root cause.
- **`headless=False` hard-coded** in `inbox_manager.py` (no CLI flag), inconsistent with `invitations_manager.py`'s `--headless` option.
- **Duplicated boilerplate** between the two scripts (logging setup, Playwright login/session flow, `.auth/state.json` bootstrap) — no shared utility module.
- **`ruff` line-length = 1000** effectively disables meaningful line-length linting.
- No dependency pinning strategy beyond a couple of version pins (`pydantic-ai==1.0.0b1` is a beta pinned exactly; others unpinned/minimum-only) — risk of silent breakage.

## Unenforced Rules

- **System-prompt business rules are purely LLM-judgment-based, not code-enforced**: "always ignore wealth/financial advisors," "always ignore coaches," "ignore recruiters" are text instructions to the model with no deterministic keyword/regex guard — no fallback if the LLM misclassifies.
- **`.pre-commit-config.yaml`** exists (ruff, yaml/whitespace checks) but there's no CI workflow that runs pre-commit/lint/tests on PRs — only `azure-dev.yaml` (deploy) and `template-validation.yaml` (Microsoft template checks) exist; no `lint.yaml`/`test.yaml`.
- **No branch protection or required-status-check enforcement visible** in-repo (can't verify GitHub settings from code alone).
- **No schema validation** on `linkedin_invitation_cases.yaml` writes — `run_and_log_agent` appends freeform YAML with no dedup/validation, so it can grow unbounded or get corrupted by concurrent runs.
